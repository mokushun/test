## 1. 目的

小学生が遊んでいて「サイコロを振るのが楽しい」「県を獲得した達成感がある」「対決が盛り上がる」と感じられる演出を追加する。

見た目だけを強化し、ゲームルール・勝敗・移動・得点・カード所有などの既存ロジックは変更しない。派手な演出を常時出すのではなく、重要な場面に絞る。

## 2. 作業前に必ず確認すること

1. 作業場所の `RULES.md` と `PROGRESS.md` を読む。
2. `game/todofuken-board/README.md` を読む。
3. `game/todofuken-board/index.html` の最新状態を読み、既存の演出・CSS・関数を確認する。
4. 特に以下を確認する。
   - 3Dサイコロ：`setDiceFace()`、`rollDiceAnimated()`、`dice-wrap`、`dice-cube`
   - オーバーレイ：`diceOverlay`、`showDice()`、`hideDice()`
   - 県の獲得・奪取：`resolveArrival()`、`showSplash()`、`showCardPopup()`
   - 地方ボーナス：地方ごとの所有県数・得点を更新している箇所
5. 現在の実装を尊重し、同じ機能を重複して作らない。既存の関数名やDOM構造が変わっていたら、現状に合わせて設計し直す。

## 3. 演出の実装順

### 第1段階：サイコロが画面上を転がる

現在のサイコロは6面のCSS 3Dキューブで、タップ後にその場で回転して出目が正面に止まる。これを、画面上を移動しながら転がる演出にする。

**目指す見た目**
- サイコロがタップされたら、少し弾んでから画面内を斜め方向などに転がる。
- 転がっている間は複数回転し、最後に出目が正面を向いて止まる。
- 着地時に小さく跳ねる、または一瞬だけ縮むなど、止まった感触を出す。
- 画面外へ消えない。スマートフォンでもPCでも見切れない。
- 毎回まったく同じ動きにならない程度の変化は歓迎。ただし出目と最終面の対応は必ず正確にする。

**実装上の注意**
- 物理シミュレーションは不要。CSS keyframes または Web Animations API による演出でよい。
- 既存の3Dキューブの回転と、移動アニメーションの transform が競合しないようにする。推奨は、外側の要素（ボタンまたは専用ラッパー）で移動・バウンド、内側の `.dice-cube` で3D回転を担当する構成。
- 現在の `setDiceFace()` が設定する最終姿勢を壊さない。アニメーション終了後に出目が正面を向いていること。
- タップ可能状態の `cubeWiggle` と、ロール中のアニメーションを同時に動かさない。
- `rollDiceAnimated()` は手番・対決・CPUのロールで共通利用されている。すべてのロールで自然に動くこと。
- 既存の待ち時間を見直し、演出が終わる前に次の処理へ進まないようにする。逆に待ちすぎてテンポを悪くしない。
- `prefers-reduced-motion: reduce` の場合は、移動量・回転量を大幅に減らすか、短い簡易表示にする。機能自体は止めない。
- アニメーション中に二重タップしても、ロールが二重実行されないこと。

**完了条件**
- 1〜6の全出目で、表示された目と実際の結果が一致する。
- 通常の手番、対決の攻撃・防衛、CPUのロールで動く。
- PCとスマートフォンの画面幅で、サイコロが見切れない。
- アニメーション終了後にサイコロが正しい向きで静止する。
- 既存のゲーム進行・操作に影響しない。

### 第2段階：県を獲得したときの「GET！」演出

未所有の県に到着して獲得したとき、または対決に勝って県を奪取したときに、達成感のある演出を加える。

**目指す見た目**
- 画面中央に「青森県 GET！」のように県名を大きく表示する。
- 県名の周囲に星・紙吹雪・光などを短時間だけ表示する。
- 地図上の該当県が、獲得したプレイヤーの色に変わる瞬間を目立たせる。
- 既存のカードポップアップにつながり、カードを見せる流れを維持する。
- 新規獲得と対決による奪取は、文言や色で区別してもよい。

**実装上の注意**
- 既存の `showSplash()` とスプラッシュDOMを優先的に再利用する。新しいオーバーレイを作る場合は、既存のカード・サイコロ・対決オーバーレイと重なりや操作が競合しないこと。
- 既存の `resolveArrival()` の所有者更新、カード数更新、`renderAll()`、カード表示の順序を壊さない。
- 演出は短く（目安0.8〜1.5秒）。カードポップアップを閉じられなくしたり、長時間操作を止めたりしない。
- CPUが獲得した場合も、画面上で何が起きたか分かるようにする。
- 自分の県に到着しただけの場合はGET演出を出さない。

**完了条件**
- 未所有県の獲得、対決勝利による奪取、対決敗北、自分の県への到着をそれぞれ確認し、正しい場面だけGET演出が出る。
- 地図の色、所有者、カード一覧、カード数が従来どおり一致する。

### 第3段階：対決演出の強化（第1・第2段階の安定後）

既存の対決開始・勝敗スプラッシュを活用し、攻撃側と防衛側が分かりやすい演出にする。

- 「挑戦者 VS 所有者」と対象県名を表示する。
- 相手の出目、自分の出目、所有者の防衛＋1を混同しない表示にする。
- 勝敗時は「奪取成功！」「防衛成功！」を大きく表示する。
- 演出中も勝敗ロジックは変更しない。同点は所有者の勝ち。
- CPU同士の対決も、結果が分かる程度の簡潔な表示にする。

### 第4段階：地方制覇・最終結果（必要性を見て実装）

- 同じ地方の3県目を獲得して地方ボーナス条件を満たしたとき、「東北地方 制覇！」などを短く表示する。
- 3県未満になってボーナスを失った場合も、得点変化が分かるようにする。
- 最終結果では1位・同点優勝・各プレイヤーの得点内訳を見やすくする。既存の同点優勝ルールを維持する。
- 紙吹雪や祝福演出は最終結果などの特別な場面に限定する。

## 4. デザイン・操作の共通ルール

- 小学生が見て直感的に分かる言葉を使う。「獲得」「GET」「防衛成功」など短く。
- 画面を常に動かさない。演出は重要イベントのときだけ。
- 文字やボタンを隠さない。特にスマートフォンの縦画面で確認する。
- 色だけに頼らず、文字・アイコンでも意味を伝える。
- 既存のプレイヤー色・県の所有色・地方色と矛盾させない。
- 効果音を追加する場合は別段階とし、初期状態は音量に配慮する。ブラウザの自動再生制限を守り、ユーザー操作後にだけ再生する。ミュート手段を用意する。
- 外部ライブラリや外部画像素材は原則追加しない。CSS・HTML・既存データを優先する。
- `prefers-reduced-motion` に対応する。

## 5. 変更してはいけないゲームルール

以下はユーザー決定済み。演出の実装で変更しない。

- プレイ人数は2〜3人。
- 2人は北海道・沖縄、3人は北海道・沖縄・静岡から開始。
- 手番順はランダム。
- 各プレイヤー12回ずつ手番を行ったら終了。
- サイコロの出目の数だけ道路に沿って移動する。分岐では行き先を選ぶ。
- 通過した県は取得しない。移動終了時に到着した県だけが対象。
- 未所有県に到着したら獲得する。
- 他プレイヤーの所有県に到着したら対決。所有者は防衛＋1、同点は所有者の勝ち。
- 自分の所有県に到着した場合は何も起きない。
- 同じ地方の県を3つ以上所有すると、その地方ごとに＋3点。3県未満になるとボーナスを失う。
- 最終得点は所有県1県につき1点＋地方ボーナス。
- 合計点と所有県数が同点なら同点優勝。

## 6. テスト・検証

各段階で次を確認する。

1. JavaScript構文エラーがない。
2. ゲーム開始から12ターン終了まで完走できる。
3. 2人・3人の両方で確認する。
4. 人間のロール、CPUのロール、対決の攻撃・防衛を確認する。
5. 未所有県の獲得、他プレイヤー県の奪取・防衛、自分の県への到着を確認する。
6. 分岐選択・地図スクロール・カード表示・最終結果が従来どおり動く。
7. 画面幅の異なるPC・スマートフォンで、演出やボタンが見切れない。
8. アニメーションを短縮する設定でも操作できる。
9. 可能なら固定乱数やDOMテストで、全出目と各イベントの表示条件を検証する。実機ブラウザ確認は別途ユーザーにも依頼する。

テストで問題が出た場合は、演出を簡略化してでも既存のゲーム進行と操作性を優先する。
